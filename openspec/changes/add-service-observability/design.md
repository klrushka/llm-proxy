## Context

`internal/metrics` хранит наблюдения за последнюю минуту и отдаёт шесть гаужей. Замеряется только `POST /process`. Доступ к `/metrics` идёт через consumer access: в `checker` — `403`, в `production` — Bearer-ключ потребителя, а `/process` там запрещён. Ни один профиль не даёт рабочих метрик.

## Goals / Non-Goals

**Goals:**
- Метод RED для каждого маршрута и каждой внешней зависимости.
- Метрики агрегируются между инстансами и за любой период: счётчики и гистограммы вместо оконных гаужей.
- Названия и метки совместимы со стандартными дашбордами и правилами: OpenTelemetry semantic conventions, правила именования Prometheus.
- Сборщик получает метрики в обоих профилях без ключа потребителя.
- Ни одна метка не может содержать ПДн или идентификатор запроса.

**Non-Goals:**
- Трассировка и экспорт по OTLP.
- Метрики внутри Python worker: Go-клиент видит длительность, доступность и `429` воркера.
- Метрики качества детекции (precision/recall) — они считаются harness-ом офлайн.
- Изменение семантики `/health/ready`.

## Decisions

1. **Библиотека `prometheus/client_golang`.** Это официальная библиотека Prometheus и основной выбор для Go-сервиса, который опрашивает Prometheus. Она даёт `go_*` и `process_*` метрики из коробки.

   Альтернатива: OpenTelemetry Go SDK с Prometheus-экспортером. Отклонено для этой change: у сервиса нет трассировки и OTel Collector, SDK тянет заметно больше зависимостей. Названия метрик берутся из semantic conventions OpenTelemetry, поэтому переход на OTel SDK позже не сломает дашборды. Самописная экспозиция на стандартной библиотеке отклонена: гистограммы, runtime-метрики и формат лучше брать из проверенной библиотеки.

2. **Отдельный внутренний порт для `/metrics`.** Порт метрик закрывается сетью (NetworkPolicy, `expose` в compose), а не ключом потребителя. По умолчанию `127.0.0.1:9464` — порт Prometheus-экспортера OpenTelemetry; `9090` не используется, чтобы не конфликтовать с самим Prometheus.

   Альтернатива: открыть `/metrics` на API-порту в `checker` и выдать сборщику ключ в `production`. Отклонено: ключ потребителя даёт доступ к data-маршрутам, а открытый `/metrics` на публичном порту раскрывает профиль нагрузки.

3. **Имена по OpenTelemetry semantic conventions.** `http.server.request.duration` (Stable) → `http_server_request_duration_seconds`, `http.client.request.duration` (Stable) → `http_client_request_duration_seconds`, `http.server.active_requests` → `http_server_active_requests`. Бакеты — рекомендованные спецификацией `0.005 … 10` с, плюс `30` и `60` для вызовов LLM.

4. **`http_route` — шаблон маршрута.** Берётся из фиксированного соответствия метода и пути (как в `audit.operationFor`), значение — шаблон `/v1/pii/scopes/{scope_id}`, никогда не фактический путь. Нераспознанный путь получает `http_route=""` и не порождает новых рядов. Middleware стоит снаружи access control и admission, поэтому `401`/`403`/`429` попадают в метрики.

5. **Доменные метки из закрытых перечислений.** `type` в `pii_entities_detected_total` — только типы из canonical registry. `pii_vault_mappings` — число записей без каких-либо меток.

6. **Алерты по SLO.** По умолчанию: доступность 99,5 % (доля ответов не `5xx`) и p95 < 1 с для `POST /v1/runtime/chat` без учёта LLM. Ошибки — multi-window burn-rate алерты (Google SRE Workbook). Отдельные алерты: сервис не опрашивается, model worker недоступен, устойчивые `429`, рост `pii_vault_mappings`.

## Risks / Trade-offs

- [Удаление старых гаужей ломает внешних потребителей] → старые имена перечислены в README как удалённые; дашборд обновляется в этой же change.
- [Порт метрик забыли закрыть сетью] → по умолчанию слушает `127.0.0.1`; в compose только `expose`; runbook описывает NetworkPolicy.
- [Накладные расходы при 1000 RPS] → client_golang пишет атомарно без аллокаций на hot path; проверяется load bench.
- [Цели SLO условные] → пороги вынесены в начало `alerts.yml` и меняются без правки выражений.
