## Context

Сейчас внешний `audit.Middleware` пишет только allowlisted metadata в stderr и принципиально не принимает тела. Публичные JSON-маршруты используют общий лимит входа 8 MiB, а middleware-цепочка собирается в `cmd/pii-service`. См. мотивацию в `proposal.md` и контракт в `specs/debug-http-logging/spec.md`.

Новый журнал не должен расширять API audit logger: иначе чувствительные данные случайно попадут в обычный audit sink. Нужен отдельный компонент с отдельным жизненным циклом файла и включением только на `debug`.

## Goals / Non-Goals

**Goals:**
- Сохранять в JSONL байты публичных request/response body, которые реально прошли через HTTP handler.
- Не менять порядок обработки, ограничения размера, status, response body и существующий audit-формат.
- Ограничить область data routes фиксированным allowlist и сериализовать конкурентные записи.
- Не запускать listeners при неверном уровне или недоступном debug-файле.

**Non-Goals:**
- Логирование headers, query string, фактического URL path и сетевых адресов.
- Логирование model worker, LLM, health и metrics обмена.
- Ротация, шифрование, доставка и автоматическое удаление debug-файла.
- Динамическое изменение уровня без перезапуска процесса.
- Гарантия сохранения непрочитанной части тела запроса, если middleware до router отклонил запрос.

## Decisions

1. **Отдельный пакет debug HTTP logger.** Компонент принимает только method, route template, status и byte slices тел, кодирует одну JSON-строку и пишет её под mutex. Audit logger и его allowlist не изменяются.

   Альтернатива: добавить тела в `audit.Event`. Отклонено, потому что один тип события и один sink смешают эксплуатационный audit и явно чувствительную диагностику.

2. **Уровень как закрытое перечисление `info|debug`.** `internal/config` нормализует регистр, задаёт `info` по умолчанию и отклоняет остальные значения. Отдельный boolean не используется, чтобы имя `PII_LOG_LEVEL` оставалось расширяемым без неявных комбинаций флагов.

3. **Фиксированный sink `/var/log/pii-service/debug.jsonl`.** При `debug` startup wiring проверяет каталог, отклоняет symbolic link, открывает обычный файл с `O_CREATE|O_WRONLY|O_APPEND` и mode `0600`, затем применяет и проверяет `0600` для уже существующего файла. Дескриптор закрывается после остановки обоих серверов. При `info` файловые операции отсутствуют.

   Альтернатива: configurable path. Отклонено по выбранному контракту; фиксированный путь упрощает эксплуатацию и исключает запись в произвольное место через environment.

4. **Захват без предварительного чтения request body.** Middleware оборачивает `r.Body` в `io.TeeReader`/`io.ReadCloser` и копит только байты, которые downstream реально прочитал. Это сохраняет текущую семантику `http.MaxBytesReader`, не перемещает дорогое чтение перед admission и не запускает обработку повторно. Для штатных JSON handlers тело читается полностью; ранние `429`/`503` могут иметь пустой или частичный request body, что явно отражает фактически обработанные данные.

   Альтернатива: заранее прочитать тело целиком и восстановить `r.Body`. Отклонено из-за дополнительной задержки до admission, двойного удержания до 8 MiB на запрос и риска изменения обработки oversized/streaming input.

5. **Захват ответа прозрачным writer wrapper.** Wrapper записывает status при первом `WriteHeader`, считает неявный `200` на `Write`, копирует фактически переданные bytes и предоставляет `Unwrap() http.ResponseWriter` для `http.ResponseController`. Реализация сохраняет поддерживаемые исходным writer optional interfaces, не объявляя неподдерживаемые возможности.

6. **Middleware после admission, до router.** Цепочка становится `audit -> metrics -> admission -> debug -> router`. Так raw bodies создаются только для допущенных data-запросов, health остаётся вне allowlist, а metrics listener вообще использует другой server. Route resolver возвращает только шаблон mux; неизвестные routes не логируются.

7. **JSON string для тел.** Request и response body кодируются стандартным JSON encoder как строки: JSONL остаётся валидным для корректных, malformed и пустых тел, а escape-последовательности однозначно восстанавливаются после JSON decode. Событие содержит `timestamp`, `method`, `route`, `status`, `request_body`, `response_body`.

8. **Ошибка записи не влияет на клиента.** Запись выполняется после возврата downstream handler. Ошибка sink не меняет уже сформированный ответ и не вызывает retry; в stderr выводится фиксированная строка без ошибки ОС и без event payload, чтобы путь или содержимое не утекали через второй лог.

## Risks / Trade-offs

- [Debug-файл содержит PII, восстановленный текст и токены] → режим по умолчанию `info`, явное предупреждение в README/runbook, права `0600`, отдельный volume и ручная политика удаления.
- [Append-файл растёт без ограничения] → документация требует внешнюю ротацию/ограничение времени debug-сессии; встроенная ротация остаётся вне scope.
- [Копирование тел увеличивает память и CPU] → захватываются только уже читаемые данные, действует существующий лимит request body; нагрузочный тест сравнивает `info` и `debug`.
- [Ранний отказ не читает входное тело] → журнал честно хранит только фактически прочитанные bytes; предварительное чтение намеренно не применяется.
- [Сбой диска после старта теряет debug-события] → клиентский контракт не ломается, stderr получает безопасный сигнал, эксплуатационный мониторинг следит за ним.
- [Конфликт с активными planning artifacts о запрете body logging] → перед архивированием изменений конфликтующий audit-сценарий в `add-reversible-russian-pii-protection` должен быть пересмотрен либо это изменение должно архивироваться позже него как явная замена.

## Migration Plan

1. Развернуть образ без `PII_LOG_LEVEL`: поведение останется `info`, новый файл не создаётся.
2. Для диагностической сессии создать `/var/log/pii-service` с доступом только service user и подключить защищённый volume при необходимости сохранения файла.
3. Перезапустить с `PII_LOG_LEVEL=debug`, проверить mode `0600` и появление JSONL-событий на synthetic запросе.
4. После диагностики вернуть `PII_LOG_LEVEL=info`, перезапустить сервис и безопасно удалить или изолировать файл согласно локальной политике хранения.
5. Rollback выполняется возвратом старого образа; формат публичного HTTP API и audit JSON при этом не меняется.
