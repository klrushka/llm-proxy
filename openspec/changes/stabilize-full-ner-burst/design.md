## Context

В `ce8129` Go допускает до 64 HTTP requests и отвечает `429` сверх этого числа. `InferBounded` сначала вызывает `PlanWindows`, затем `InferWindows`. Глобальный Go semaphore размера 4 удерживается только вокруг отдельных `/infer` calls; `/plan_windows` не ограничен им. Python worker допускает четыре дорогостоящие POST операции суммарно и сразу возвращает `503` при переполнении. Go относит любой worker non-2xx к `ErrModelUnavailable`. `process.Operation` переводит ошибочный claim в terminal expired, сохраняя отказ для будущих повторов.

Суммарный бюджет проверки одного запроса — 10 секунд с двумя повторами по исходному OpenSpec. Из ~983 новых ID за 6 секунд следует средняя входная скорость ~164 ID/s. Если все 983 поступили в течение 6 секунд и должны завершиться не позже 10 секунд после последнего прихода, теоретический минимум — 983/(6+10) ≈ 61,4 успешных ID/s; распределение индивидуальных deadlines может поднять необходимую скорость. Обезличенная агрегация более широкого 10-секундного окна дала 1005 ID, но лишь 448 точных текстов. При идеальном устранении повторных NER это 2,24 ID на один fresh NER и всё равно 448 новых модельных обработок: ни один текст не встречался в ранее успешной части доступного журнала. Нельзя обещать нужный goodput при неизвестном реальном времени обеих моделей на 4 vCPU. Очередь только сглаживает короткий пик, а не повышает steady-state throughput.

## Decisions

1. **Один бюджет worker для всех его POST.** Общий permit в `modelclient.Client` выдаётся перед каждым `/plan_windows` и `/infer`, а не только перед inference. Ожидание завершается по исходному контексту/общему timeout. Никаких независимых повторов внутри клиента: checker уже повторяет запрос. Не повышать Python `MAX_INFLIGHT` без профиля CPU/RAM.
2. **Ограниченная очередь до claim.** На Go HTTP boundary допускаются только запросы, которые укладываются в измеренный ресурсный и deadline budget. Число ожидающих и общий размер их тел ограничены; при переполнении безопасный `429`/`Retry-After`, без `result` и без создания `payload_id` claim. Нельзя оставлять занятую очередь после отмены клиента. Защищённые health/metrics остаются доступными.
3. **Временная ошибка не является окончательным результатом ID.** Claim существует только до завершения первой попытки. При transport/worker busy/cancellation он безопасно завершается для текущих waiters, после чего тот же исходный payload может получить новый atomic claim. Конфликтующий payload для того же ID не должен стать новым владельцем в гонке. Не удалять запись вслепую, если mask мог успеть выдать/stash mapping или завершиться после отмены; сначала доказать отсутствие частичного опубликованного результата и безопасную компенсацию/повтор.
4. **Повторный NER только там, где это безопасно.** Обёртка над полным `InferBounded` может хранить ограниченное число успешно проверенных span results по HMAC текста с одноразовым ключом процесса плюс идентичность модели/режима; хранить plaintext, маску, vault mapping или результат policy нельзя. Короткий TTL/лимит байтов/entries и in-flight coalescing допускаются только после проверки на реальной синтетической повторяемости, отмену, ошибки и restart. Каждый новый `payload_id` всё равно проходит Go merge/ownership/tokenization и получает свой record. Считать cache hit отдельно от fresh inference; никакой claim о fresh throughput на основе hit.
5. **Сначала профиль, затем одно узкое ускорение.** Считать долю времени `plan_windows`, RuBERT, GLiNER, Go merge/tokenization и разрешённого debug I/O отдельно, а также useful full-NER goodput, RAM peak и CPU. Если для короткого текста planning доминирует, объединить проверку токенов и infer в worker в одном вызове, сохранив точный RuBERT tokenizer limit, long-text окна, оба model sources и UTF-8 offsets. Если доминирует inference, сравнить worker inflight 4 и 8 и поддерживаемую готовыми моделями настройку CPU threads/batching на одинаковой синтетической нагрузке. Оставить 8 только если completed `200`/s вырос, p99 и 10s timeout не ухудшились, память не приближается к 8 GiB и качество осталось тем же. Не подменять full mode fast mode.
6. **Ограничение стоимости.** Для хакатона на два дня и суммарного бюджета 1000 RUB использовать одну существующую VM. Новые GPU, реплики, внешний брокер и постоянная очередь не входят в ближайший scope. Если measured full-NER goodput ниже необходимого, явно сообщить achievable envelope и невозможность гарантировать данный burst в 10s на этой VM. Разрешённый debug-журнал и существующий volume не отключать и не удалять ради бенчмарка.

## Rollout and rollback

После отдельного разрешения release развернуть новый immutable release на той же VM с существующим `hf-cache`, ключом и debug volume; smoke проверить обе модели, mask/restore и безопасный retry. На коротком canary нагрузку поднять до измеренного допустимого уровня; остановить при росте `503`, timeout, p99 или RAM к пределу 8 GiB. При регрессии вернуть прежний immutable release без удаления volumes; сначала сохранить безопасные агрегаты метрик и текущую версию. Поскольку `process.Store` и vault живут в памяти, restart теряет активные корреляции: до переключения минимизировать окно и явно учитывать это в протоколе проверки.

## Acceptance

- В synthetic concurrency тесте больше четырёх конкурентных Go-originated worker POST не достигают Python; насыщение `/plan_windows` не даёт worker `503`. Лимит очереди, deadline, отмена и освобождение permits проверены.
- Worker `503` или timeout не превращает `payload_id` в вечный `503`: поздний повтор исходного текста после восстановления получает `200`; одновременно ожидающие не запускают второе маскирование; иной текст не перехватывает ID.
- Для `200` маска/restore и оба model sources совпадают с базовым качеством; no plaintext/result on errors и отсутствие PII в logs/metrics сохраняются.
- Отчёт до/после на той же VM и одинаковом синтетическом open-loop workload указывает revision/topology, плановые и достигнутые arrival rates, completed `200`, `429`, `503`, timeout, p50/p95/p99/max для успехов отдельно, CPU/RAM peak, очередь и latency каждого worker stage. Отдельно фиксируются cache hit/miss, 983/6s burst и устойчивый **fresh full-NER** rate; критерий успеха burst задаётся по подтверждённому checker deadline, без замены им throughput claim.

## Risks

- Даже исправленный допуск будет отвечать `429` либо timeout, если входная работа объективно превышает service rate на этой VM. Большая очередь повышает tail latency и удерживает plaintext в памяти.
- Повтор после неясного частичного успеха может изменить токен/mapping; переход state machine требует теста на атомарность публикации результата и cleanup.
- Удаление отдельного planning без точной токен-границы может нарушить 100k-token safety и качество NER; выполнять только при эквивалентном тесте.
