## Purpose

Публичный API сервиса PII предоставляет обнаружение, токенизацию и восстановление без входящей авторизации, сохраняя изоляцию по явно переданному scope.

## ADDED Requirements

### Requirement: Функциональные HTTP-маршруты доступны без входящей авторизации
Система SHALL принимать запросы к `/process`, `/metrics`, `/v1/pii/detect`, `/v1/pii/tokenize`, `/v1/pii/detokenize`, удалению scope и `/v1/runtime/chat` без Bearer API key, если маршрут доступен по своей обычной конфигурации. Отсутствующий, недействительный или дополнительный `Authorization` header MUST NOT быть причиной `401` или `403`.

#### Scenario: Токенизация без Bearer header
- **WHEN** клиент отправляет валидный `POST /v1/pii/tokenize` без `Authorization`
- **THEN** система обрабатывает запрос по контракту токенизации, а не отвечает ошибкой авторизации

#### Scenario: Некорректный Bearer header не меняет доступность
- **WHEN** клиент отправляет валидный запрос к функциональному маршруту с произвольным `Authorization` header
- **THEN** система обрабатывает запрос так же, как запрос без этого header

### Requirement: Единая политика обработки для публичных запросов
Система SHALL применять единый внутренний набор всех канонических типов ПДн и разрешать detokenization для каждого публичного запроса. Клиент MUST NOT передавать identity, consumer policy или настройки разрешённых типов для выполнения API-операции.

#### Scenario: Восстановление токенов без consumer capability
- **WHEN** клиент отправляет валидный `POST /v1/pii/detokenize` для существующих токенов и того же `scope_id`
- **THEN** система восстанавливает значения по обычному контракту detokenization без проверки consumer capability

### Requirement: Конфигурация сервиса не содержит входящей авторизации
Система MUST NOT требовать, интерпретировать или документировать `PII_ACCESS_PROFILE` и `PII_CONSUMERS_JSON`. Переменная `PII_LLM_API_KEY` SHALL сохранять прежнее значение как учётные данные исходящего запроса к внешней LLM и не SHALL использоваться для аутентификации входящих HTTP-запросов.

#### Scenario: Запуск без access-конфигурации
- **WHEN** сервис запускается с обязательной vault и обычной model-конфигурацией, но без `PII_ACCESS_PROFILE` и `PII_CONSUMERS_JSON`
- **THEN** конфигурация считается валидной и сервис запускается

#### Scenario: Исходящая LLM-авторизация сохранена
- **WHEN** заданы полные настройки внешней LLM и непустой `PII_LLM_API_KEY`
- **THEN** сервис отправляет этот ключ только в исходящем запросе к настроенной LLM

### Requirement: Scope принадлежит вызывающему API контексту
Система SHALL использовать предоставленный `scope_id` как единственный namespace mappings для публичного API. Система MUST NOT изменять namespace на основе входящей идентичности, consumer ID или заголовков запроса.

#### Scenario: Повторное использование scope без идентичности
- **WHEN** клиент токенизирует текст и затем detokenize-ит выданные токены с тем же `scope_id` без identity header
- **THEN** система разрешает mappings в этом `scope_id`
